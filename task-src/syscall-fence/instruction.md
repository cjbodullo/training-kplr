ok so there's a binary at `/app/target`. point it at a job file, that is its only argument, and it does a pretty dull thing: opens some data files, reads them, adds up the numbers it finds, prints one line like `sum=70 files=2`. that is all it is for. i left a few sample jobs and their data in `/app/samples`, and `strace` is on the box, so run it a bunch and watch the syscalls go past. that is where you actually learn what it does.

now the part i care about. the moment `/app/target` starts, before it touches a single directive from the job, it reads `/app/filter.bpf` and installs it on itself. `NO_NEW_PRIVS` first, then `SECCOMP_MODE_FILTER`. after that, everything the job makes it do runs under your filter. you write that file. not a library config, not json, the actual thing the kernel takes: a flat run of `struct sock_filter` records back to back, no header, and the file is exactly 8 bytes per instruction. assume x86-64. if the file is not there the target just runs wide open, which is honestly the easiest way to see its normal behaviour before you start fencing it in.

here is the catch. most jobs are the boring read and add kind. some are not. a hostile job pushes the target into trying to mess with the box: write a new file, create one, delete or rename something, drop a hard or soft link, make a directory, exec another program, change a file's permission bits. every one of those has to come to nothing. and you have to pull that off without breaking the boring path, because the boring path still has to finish and print the right number on every input, the hostile ones included.

so you are squeezed from two sides and that is really the whole puzzle. the target has to open files, reading data is its job, so "just block file access" is off the table. but it must never open one for writing, never create one, never reach any of the mutating calls. the target is right there and so is `strace`. figure out what the honest path genuinely needs, figure out how each nasty bit actually lands in the kernel, and put the line between them in the filter. keep one thing in your head the whole time. a seccomp program only ever sees the syscall number and the plain scalar args in `seccomp_data`. it never sees the strings hanging off the pointers. so "block writes to that path" is not something you can say. you say it in numbers and flags, or you do not say it.

i grade by running `/app/target` on sealed jobs of my own. the boring ones have to exit 0 and print the exact summary. the hostile ones have to leave the filesystem exactly as it was. nothing created, written, moved, removed, executed, chmodded. how you stop a tamper is your call. hand it an errno, or kill the process outright, both are fine by me, as long as the thing never actually happens.

You have 18000 seconds to complete this task. Do not cheat by using online solutions or hints specific to this task.
